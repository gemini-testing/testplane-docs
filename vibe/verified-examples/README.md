# Проверенные примеры команд Testplane

Проект получен из отдельного проекта, созданного командой `npm init testplane@latest`. Он сохраняет исполняемые примеры для 28 новых команд и связанных исправлений существующих страниц в обеих локалях. Проверяются 86 блоков кода на 82 страницах по 41 тестовому файлу; два файла содержат по два теста. `manifest.json` связывает страницу EN, страницу RU и тест. Скрипт `verify-snippets.cjs` проверяет точное совпадение блоков JavaScript с тестовыми файлами.

## Окружение

-   Node.js 22.21.1.
-   Testplane 9.3.2 и `@testplane/webdriverio` 9.6.2; полный граф зависимостей закреплен в `package-lock.json`.
-   Chrome for Testing 150.0.7871.124, WebDriver BiDi.
-   Для `downloadFile`: Selenium Grid 4.50.0 с управляемыми загрузками и `se:downloadsEnabled: true`.
-   Исходный изолированный проект: `/private/tmp/testplane-docs-examples-20261009`.

## Запуск

Из этого каталога установите зависимости через `npm ci --legacy-peer-deps`. Флаг нужен для воспроизведения сохраненного lock-файла: в нем `@puppeteer/browsers@3.0.4` требует peer-зависимость `proxy-agent >=8.0.1`, а закреплена версия `6.5.0`. Без флага `npm ci` в npm 10.9.4 отклоняет этот граф. Зависимости и lock-файл при повторной проверке не обновлялись. `npm test` поднимает HTTP-стенд на свободном порту localhost, запускает браузерные тесты и закрывает HTTP-сервер после завершения. Сервер отдает только синтетические тестовые данные. Для получения Chrome и драйвера при первом запуске может понадобиться сеть.

`npm run check:snippets` проверяет соответствие тестов страницам; запускайте эту команду из сохраненного в репозитории каталога, а не из отдельной копии проекта.

`npm run test:selenium` запускает отдельный тест скачивания. Этот стенд рассчитан на **локальный Grid на той же машине**: HTTP-сервер слушает только `127.0.0.1`, и этот адрес передается браузеру в `baseUrl`. Grid по умолчанию ожидается на `http://127.0.0.1:4446`; другой локальный адрес или порт можно передать через `SELENIUM_GRID_URL`. Переменная `EXAMPLE_CHROME_BINARY` позволяет указать путь к браузеру на локальном узле Grid. Простая замена адреса на внешний Grid не сработает: удаленный браузер не видит локальный HTTP-стенд. Для удаленного запуска сначала нужен отдельно настроенный туннель, делающий этот loopback-адрес доступным в браузерной среде; такой запуск здесь не проверялся. Включите управляемые загрузки по [инструкции Selenium](https://www.selenium.dev/documentation/webdriver/remote_webdriver/#enable-downloads-in-the-grid).

## Изоляция и найденные ограничения

-   `retry: 0`: итоговый успех не скрывает автоматические повторы.
-   `testsPerSession: 1`: каждый тест использует новую браузерную сессию.
-   `isolation: false` и одна вкладка нужны для проверенных примеров `throttleCPU` и `throttleNetwork`: реализация обращается к первой странице Puppeteer.
-   В проверенной связке `throttleNetwork("online")` не восстанавливает сеть после `"offline"`. Пример завершает офлайн-сессию и проверяет доступность сети в следующей.
-   В WDIO 9.6.2 флаг автоматической сетевой подписки общий для модуля. Примеры моков явно вызывают `sessionSubscribe`, чтобы получать события после создания новой сессии тем же воркером.
-   `url` с `wait: "networkIdle"` в проверенной версии падает при поиске запроса навигации по context ID. Опубликованный пример использует `complete`; неуспешная диагностика сохранена отдельно.
-   Мобильные команды отложены пользователем: рабочая Appium-среда пока не предоставлена. Эти примеры и страницы не добавлялись.

## Проверка примеров в pull request

Workflow `Documentation examples` запускается на каждом PR в `master`. Он не использует секреты, S3 или права записи в репозиторий. Проверки разделены:

-   `Examples coverage` проверяет соответствие опубликованного кода тестам и контролирует новые и измененные блоки.
-   `Examples runtime (chrome)` выполняет основной набор в Chrome/BiDi.
-   `Examples runtime (selenium)` выполняет `downloadFile` в локальном Selenium Grid с управляемыми загрузками.

Чтобы эти проверки блокировали слияние, добавьте все три имени в обязательные status checks правила защиты `master`. Сам YAML не изменяет настройки защиты ветки.

На одноразовых Linux-runner GitHub Actions браузер запускается с `--no-sandbox` и `--disable-dev-shm-usage`, как в [standalone-наборе Testplane](https://github.com/gemini-testing/testplane/blob/master/test/integration/standalone/constants.ts). Это обходит ограничения sandbox для скачанного Chrome for Testing на Ubuntu. Условия задаются совместно: `GITHUB_ACTIONS=true` и `RUNNER_OS=Linux`. В обычном локальном запуске и на других платформах sandbox браузера не отключается. Не переносите эту настройку в окружение с секретами или на постоянный сервер; CI-стенд использует синтетические локальные страницы.

### Что считается покрытым

`manifest.json` связывает блок документации с полным тестовым файлом. Содержимое блока должно совпадать с файлом, включая пробелы и завершающий перевод строки. Обе локали проверяются независимо. Конфигурации Testplane получают список файлов из этого же manifest: отдельный список исполняемых примеров поддерживать не нужно.

Поля записи:

-   `page` — путь страницы относительно корня репозитория.
-   `translation` — путь перевода; необязателен для примера только в одной локали.
-   `test` — путь файла относительно этого проекта, например `examples/browser/addInitScript.testplane.js`. Допустимые каталоги определены в `suite-files.cjs`; `selenium` запускается в отдельном наборе.
-   `language` — язык блока, по умолчанию `javascript`.
-   `blockIndex` — индекс среди блоков **этого языка** на странице, начиная с нуля; по умолчанию `0`.
-   `blockCount` — необязательное ожидаемое число блоков этого языка на странице.
-   `testCount` — число тестов в файле, по умолчанию `1`. Для всех ссылок на один файл значение должно совпадать.

После запуска CI читает JSONL-результаты Testplane. Каждый заявленный файл должен дать ровно `testCount` успешных результатов. Пропуски, повторы, отсутствующие тесты и посторонние файлы завершают проверку ошибкой. Одного успешного exit code недостаточно.

### Новые примеры и накопленный долг

Инвентаризация использует AST Markdown/MDX, а не поиск только по метке `javascript`. Она учитывает блоки с любым языком и без языка, в том числе внутри вкладок. JSX-элементы `CodeBlock`, `pre` и `code` учитываются как `jsx-code`, но автоматически не исполняются. Inline-код, произвольные пользовательские React-компоненты и примеры за внешними ссылками не входят в эту проверку.

В CI базовая версия берется из `pull_request.base.sha`. Для каждой страницы сравниваются язык и SHA-256 содержимого блоков; число одинаковых вхождений тоже учитывается. Изменение обычного текста, номера строки или `title` у блока не требует новой проверки. Новый, измененный, переименованный или дополнительно скопированный пример требует покрытия. Без доступной базовой Git-ревизии проверка завершается ошибкой. Редактируемого списка «старых» примеров нет.

Неизмененные непокрытые блоки получают статус `legacy`: они видны в отчете, но не блокируют PR. Это долг покрытия, **не доказательство работоспособности и не список ошибок**. Удалить покрытие сохранившегося ранее проверенного примера нельзя: CI покажет `regression`.

Из инвентаризации исключены версии документации, включая v8, и явный список мобильных страниц в `audit-snippets.mjs`. Текущий список исключенных страниц входит в отчет. Новые мобильные страницы нужно отдельно включать в этот список при согласованном расширении мобильного раздела; запускать их на desktop-стенде не следует.

Если новый блок заведомо не является исполняемым примером — например, показывает вывод программы или сигнатуру, — добавьте точечную запись в `non-executable.json`. Укажите `page`, `language`, `blockIndex`, `sha256` и содержательный `reason`. Хеш берите из `coverage.json`: это SHA-256 UTF-8 значения AST-блока без перевода строки перед закрывающей оградой. Запись привязана к конкретному содержимому и устаревает при изменении кода. Ее нужно согласовать на ревью. Не используйте такую классификацию вместо теста для исполняемого примера. В отчете она отделена от успешного runtime-покрытия. Сейчас список пуст.

### Как добавить или изменить пример

1. Подготовьте полный тест в соответствующем каталоге `examples/`. Используйте локальный HTTP-стенд из `run-examples.cjs`, без внешних сайтов и секретов.
1. Выполните тест и перенесите тот же код в блок документации. При необходимости измените обе локали.
1. Добавьте или обновите запись `manifest.json`. Для нового типа примеров, не поддерживаемого этим Testplane-стендом, сначала добавьте исполняемый адаптер и его проверку, а не исключение из покрытия.
1. Из корня репозитория выполните:

    ```bash
    npm ci
    npm run test:examples:unit
    npm run check:examples -- --base origin/master
    ```

1. Из этого каталога выполните полный основной набор:

    ```bash
    npm ci --legacy-peer-deps
    node run-ci.cjs chrome
    ```

Для Selenium установите Java 21, скачайте `selenium-server-4.50.0.jar` из [официального релиза Selenium](https://github.com/SeleniumHQ/selenium/releases/tag/selenium-4.50.0) и укажите абсолютный путь в `SELENIUM_JAR`. Затем выполните `node run-ci.cjs selenium`. Скрипт проверяет SHA-256 JAR, устанавливает браузер и драйвер, поднимает свой Grid на `127.0.0.1:4446`, дожидается готовности и останавливает его после теста. Порт должен быть свободен. `JAVA_BINARY` позволяет указать отдельный Java executable. Существующий внешний Grid этот CI-runner не использует.

`run-ci.cjs` опирается на внутренний установщик закрепленной версии Testplane, как standalone-workflow самого фреймворка. При обновлении Testplane проверяйте совместимость этого адаптера. Chrome закреплен в `testplane.config.js`, зависимости — в lock-файле. Эта итерация проверяет воспроизводимость на закрепленном окружении, а не совместимость со всеми браузерами или последним npm-релизом.

### Где смотреть результаты

В GitHub Actions доступны краткие Job Summary и три артефакта со сроком хранения 14 дней:

-   `doc-examples-coverage`: `coverage.json`, полный `coverage.md` со всеми старыми непокрытыми блоками, короткий `summary.md`.
-   `doc-examples-chrome`: лог Testplane, JSONL-результаты, сведения об окружении и итог runtime-проверки.
-   `doc-examples-selenium`: те же файлы и лог Grid.

Артефакты загружаются и при падении проверки. Ошибка установки окружения не считается успешным прогоном. Локальные результаты по умолчанию лежат в `tmp/doc-examples/` от корня репозитория и `artifacts/` этого проекта. Для разделения прогонов можно задать `EXAMPLE_ARTIFACTS`. Эти каталоги не коммитятся. Файлы в `evidence/` сохраняют историю прежней ручной валидации и не используются как подтверждение текущего CI-прогона.
