# Проверка примеров документации

Исполняемый пример хранится только в документации. Генератор извлекает размеченные блоки MDX и создает тесты для Testplane. CI генерирует их заново при каждом запуске: писать `.testplane.js` и поддерживать manifest вручную не нужно.

Проверяются текущие страницы EN/RU. Мобильные страницы и версионированная документация, включая v8, исключены. Старые непокрытые блоки остаются в отчете как долг покрытия.

## Добавление примера

Добавьте к ограде блока `javascript` или `js` метку `testplane=<stable-id>`. Внутри должен быть полный CommonJS-тест с проверкой ожидаемого результата, например:

````markdown
```javascript testplane=page-heading
const assert = require("node:assert/strict");

it("page heading: show the command examples page", async ({ browser }) => {
    await browser.url("/");
    assert.equal(await browser.$("h1").getText(), "Command examples");
});
```
````

Идентификатор состоит из строчных латинских букв, цифр и дефисов. Для разных примеров используйте разные идентификаторы. Для перевода EN/RU и повторной публикации того же примера на другой странице используйте один идентификатор: код должен совпадать точно, и тест запустится один раз. Повтор идентификатора внутри одной страницы считается ошибкой.

По умолчанию пример выполняется в Chrome/BiDi. Для примера, которому нужен Selenium Grid, добавьте `suite=selenium` после идентификатора. Существующие метаданные блока, например `title="example.js"`, можно оставить.

Генератор поддерживает прямые вызовы `it("название", callback)` на верхнем уровне, объявления переменных и вспомогательных функций. В одном блоке можно объявить несколько тестов с разными строковыми названиями; их число вычисляется автоматически по AST JavaScript. `describe`, условная регистрация, `it.only`, `it.skip`, generator-функции в callback, pending-тесты и короткие фрагменты без `it` не поддерживаются. Генератор не дописывает assertions и не исполняет код во время извлечения.

Используйте локальный HTTP-стенд из `run-examples.cjs`: синтетические страницы и API, без внешних сайтов и секретов. Если примеру нужны новые страницы или ответы API, добавьте их в этот стенд. Неизвестные переменные и отсутствующее окружение генератор не придумывает.

## Установка и запуск

Используйте Node.js 22.21.1. Из корня репозитория установите зависимости документации и Testplane:

```bash
npm ci
npm --prefix test/doc-examples ci --legacy-peer-deps
```

Флаг `--legacy-peer-deps` воспроизводит сохраненный lock-файл Testplane: `@puppeteer/browsers@3.0.4` требует peer-зависимость `proxy-agent >=8.0.1`, а закреплена версия `6.5.0`. Парсеры документации устанавливаются корневым `npm ci`; они нужны и для браузерного запуска.

После изменения примера проверьте покрытие и запустите Chrome-набор из корня репозитория:

```bash
npm run check:examples -- --base origin/master
npm run test:examples
```

-   `check:examples` проверяет новые и измененные блоки относительно Git-базы, корректность разметки тестов и совпадение кода и набора (`suite`) у блоков с одним ID. Наличие перевода он не проверяет. Успешная генерация еще не означает, что тесты прошли.
-   `generate:examples` создает `generated/chrome/`, `generated/selenium/` и `generated/manifest.json` внутри этого каталога. Обновление примера меняет сгенерированный тест, удаление убирает его. Каталог полностью принадлежит генератору; ручные файлы в нем не сохраняйте.
-   `test:examples` повторяет генерацию и выполняет весь Chrome-набор, затем проверяет JSONL-результаты. Отдельно запускать `npm run generate:examples` нужно только для просмотра сгенерированных файлов без браузера.

Для отладки одного теста укажите его название. Например, `npm --prefix test/doc-examples test -- --grep "^execute:"` запустит пример из справочника `browser.execute`. Этот запуск тоже генерирует тесты, но не заменяет полный прогон CI.

Для Selenium установите Java 21 и скачайте `selenium-server-4.50.0.jar` из [официального релиза Selenium](https://github.com/SeleniumHQ/selenium/releases/tag/selenium-4.50.0). Укажите абсолютный путь к JAR:

```bash
SELENIUM_JAR=/absolute/path/selenium-server-4.50.0.jar npm run test:examples:selenium
```

Скрипт проверяет SHA-256 JAR, запускает собственный Grid с управляемыми загрузками на `127.0.0.1:4446` и останавливает его после тестов. Порт должен быть свободен. Через `JAVA_BINARY` можно указать абсолютный путь к Java. Внешний Grid не используется: браузер должен видеть HTTP-стенд на той же машине.

## Новые блоки и накопленный долг

Инвентаризация учитывает блоки любого языка и без языка, в том числе внутри вкладок MDX. JSX-элементы `CodeBlock`, `pre` и `code` учитываются как `jsx-code`, но не генерируются в тесты. Inline-код, произвольные React-компоненты и примеры по внешним ссылкам не входят в проверку.

База в CI — `pull_request.base.sha`, локально ее нужно явно передать через `--base`. Проверка сравнивает страницу, язык, SHA-256 содержимого и число одинаковых вхождений. Правка обычного текста, номера строки или `title` у блока не требует нового покрытия.

Новый, измененный, перенесенный на другую страницу или дополнительно скопированный блок без покрытия завершает проверку ошибкой. Сообщение содержит файл, строку и подсказку: пометить полный тест через `testplane=<stable-id>` и запустить `npm run generate:examples`. Для неисполняемого блока нужна отдельная классификация с причиной. Сам генератор не превращает произвольный непомеченный текст в тест.

Неизмененные непокрытые блоки получают статус `legacy`: они видны в отчете, но не блокируют PR. Это долг покрытия, **не доказательство работоспособности и не список ошибок**. Удаление метки у сохранившегося ранее проверенного примера дает `regression`. История покрытия читается из базовой Git-ревизии, а не из редактируемого списка долга.

Для заведомо неисполняемого блока, например вывода программы или сигнатуры, добавьте запись в `non-executable.json`: `page`, `language`, `blockIndex`, `sha256` и содержательный `reason`. Хеш берите из `coverage.json`. Индекс считается среди блоков этого языка на странице с нуля. Классификация привязана к содержимому и устаревает при его изменении; ее нужно согласовать на ревью. Не используйте ее вместо теста для исполняемого примера.

Явный список исключенных мобильных страниц находится в `doc-sources.mjs` и выводится в отчет. Мобильные примеры нельзя добавлять в desktop-набор без отдельного стенда.

## Проверки и отчеты CI

Workflow `Documentation examples` выполняет три проверки на каждом PR в `master`:

-   `Examples coverage` — unit-тесты проверяющих скриптов и контроль новых и измененных блоков.
-   `Examples runtime (chrome)` — генерация из MDX и запуск основного набора в Chrome/BiDi.
-   `Examples runtime (selenium)` — генерация и запуск примеров с `suite=selenium` в локальном Selenium Grid.

Runtime-проверка требует ровно столько успешных тестов в каждом файле, сколько объявлено в исходном примере. Пропуски, повторы, отсутствующие тесты и посторонние результаты завершают проверку ошибкой. Одного успешного exit code недостаточно. Ошибка генерации останавливает запуск, а прежние сгенерированные файлы удаляются, чтобы не запустить устаревшие тесты.

Для блокировки слияния добавьте все три проверки в обязательные status checks защиты `master`. YAML не меняет настройки защиты ветки.

GitHub Actions публикует краткие Job Summary и артефакты на 14 дней, в том числе при падении:

-   `doc-examples-coverage` — `coverage.json`, полный `coverage.md` со старыми непокрытыми блоками и `summary.md`.
-   `doc-examples-chrome` — сгенерированные тесты и manifest, лог Testplane, JSONL-результаты, сведения об окружении и итог проверки запуска.
-   `doc-examples-selenium` — те же файлы и лог Grid.

Локальные отчеты сохраняются в `tmp/doc-examples/` от корня репозитория и в `artifacts/` этого каталога. Путь результатов запуска можно изменить через `EXAMPLE_ARTIFACTS`. Сгенерированные тесты, manifest, отчеты и логи игнорируются Git и не коммитятся.

## Окружение

-   Testplane 9.3.2 и зависимости закреплены в `package-lock.json`, Chrome for Testing 150.0.7871.124 — в `testplane.config.js`. При первом запуске нужна сеть для скачивания браузера и драйвера.
-   `run-ci.cjs` использует внутренний установщик Testplane. При обновлении зависимости проверяйте совместимость этого адаптера.
-   `retry: 0` запрещает автоматические повторы, `testsPerSession: 1` создает новую сессию для каждого теста.
-   `isolation: false` и одна вкладка нужны для `throttleCPU` и `throttleNetwork`: реализация обращается к первой странице Puppeteer. После `throttleNetwork("offline")` проверка доступной сети выполняется в новой сессии.
-   Примеры моков явно вызывают `sessionSubscribe`, чтобы получать события в новой сессии того же воркера WDIO.
-   На одноразовых Linux-runner GitHub Actions используются `--no-sandbox` и `--disable-dev-shm-usage`. Настройка включается только при `GITHUB_ACTIONS=true` и `RUNNER_OS=Linux`; обычный локальный запуск сохраняет sandbox. Не переносите этот режим в окружение с секретами или на постоянный сервер.
-   Проверка подтверждает работу на закрепленных версиях, а не совместимость со всеми браузерами или последним npm-релизом.
