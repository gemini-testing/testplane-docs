# Проверка примеров документации

CI читает текущие страницы EN/RU и генерирует тесты из опубликованных блоков MDX. Он запускает весь подключённый набор на каждом PR в `master`, даже если сам пример в PR не менялся. Для нового или изменённого блока без проверки CI укажет страницу, строку и причину. Мобильные страницы и версии документации, включая v8, в проверку не входят.

## Как подключить короткий пример

Не переписывайте фрагмент как отдельный тест. Укажите идентификатор примера и фикстуру — код, который подготавливает страницу или состояние для теста. Например, эти два блока на одной странице образуют **один** тест:

````markdown
```html testplane-html=element-html
<button id="save">Save</button>
```

```javascript testplane=save-button-text fixture=element-html
const assert = require("node:assert/strict");

assert.equal(await browser.$("#save").getText(), "Save");
```
````

CI загрузит указанный HTML в Chrome и выполнит JavaScript на этой странице. Изменение `Save` только в HTML сломает тест. Блок `testplane-html` должен использоваться хотя бы одним тестом **на той же странице**. Если нужна новая фикстура, добавьте её в `fixtures/`. Для `fixture=group-variant` без HTML вызывается `setup(browser, "variant")` модуля `group.cjs`. Для примера с HTML объявите вариант в `htmlVariants`: после загрузки страницы CI вызовет необязательный `afterHtml(browser, variant)`. В `verify` можно проверить побочный эффект, например содержимое записанного файла. Не дублируйте в фикстуре сам пример.

-   Для короткого фрагмента поддерживаются `js`, `javascript`, `ts` и `typescript`. Внутри доступны `browser` и Testplane `expect`. Все остальные импорты, включая `node:assert/strict`, указывайте в самом примере, чтобы его можно было скопировать в обычный тест. Проверяйте наблюдаемый результат, а не только вызов метода.
-   Самостоятельный блок с `it("название", callback)` достаточно пометить `testplane=<id>`. С фикстурой допускаются также статические `describe` и хуки. Пропущенные тесты, условная регистрация и `it.only` не подходят. При необходимости импортируйте `assert` в самостоятельном тесте.
-   Используйте одинаковый идентификатор (строчные буквы, цифры, дефисы) для одинакового примера в разных локалях. Один и тот же код с теми же входными данными запускается один раз. Если переведены строки или комментарии, укажите разные идентификаторы — выполнятся обе версии.
-   По умолчанию тест работает через WebDriver BiDi. Для API, доступного только через CDP, добавьте `transport=cdp`: CI запустит его в том же локальном Chrome, но не в BiDi-наборе. Selenium Grid не используется.

## Как проверить пример проекта

Добавьте к ограде блока `testplane-project=<тип>`. Такие проверки используют отдельный временный проект с установленной из lockfile версией Testplane, а не заглушку команды.

| Тип          | Что действительно проверяется                                                                                                                                                                                                                                                             |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `config`     | Testplane загружает декларативные настройки JS/TS. Фикстура дополняет опущенные базовые возможности браузера, но не подменяет значения примера. Это не запуск всех плагинов и хуков из конфигурации.                                                                                      |
| `cli`        | Установленный локально CLI выполняет указанные команды; тест сверяет обнаруженные тесты, результат запуска, справку, настройки или содержимое выходного файла. Поддерживаются только команды и аргументы из `project-recipes.mjs`. Произвольный shell, установки и деплой не выполняются. |
| `event`      | Реальная сессия Testplane вызывает обработчики из документации в главном процессе или воркере. Отдельный сценарий специально создаёт успешный, упавший и пропущенный тест и повтор; CI сверяет ожидаемые исходы и факт вызова каждого обработчика.                                        |
| `collection` | Testplane читает файлы тестов из временного проекта. Проверяются реальные результаты выбора тестов, работа методов `TestCollection` и хелперов `skip`, `only`, `also`. Браузер для чтения коллекции не запускается.                                                                       |
| `reporter`   | Установленный `html-reporter` строит отчёт по реальному запуску Chrome. Сценарии проверяют конфигурацию, события, результаты CLI и данные созданного отчёта.                                                                                                                              |

Например, для короткого блока с `npx testplane list-tests --browser chrome` достаточно `bash testplane-project=cli`. Одинаковые исходники одного типа в разных локалях проверяются один раз. Если для примера не подходит ни одна фикстура, добавьте проверку поведения; не помечайте его проверенным по результату разбора синтаксиса.

## Локальный запуск

Из корня репозитория:

```bash
nvm use 22.21.1
npm ci
npm --prefix test/doc-examples ci --legacy-peer-deps
npm run check:examples -- --base origin/master
npm run test:examples
```

`check:examples` проверяет разметку и покрытие относительно указанного Git-коммита. `test:examples` сам перегенерирует тесты, запускает их и сверяет JSONL с манифестом. Чтобы только посмотреть сгенерированные файлы, выполните `npm run generate:examples`. Генерируемые файлы, отчёты и логи не нужно коммитить.

Версии Testplane и зависимостей закреплены в lockfile тестового проекта, версия Chrome for Testing — в конфигурации тестов. При первом запуске установщику Testplane нужен доступ к сети для скачивания Chrome и драйвера. В основном браузерном наборе `retry: 0`, для каждого теста создаётся новая сессия.

## Что означает отчёт PR

-   `Examples coverage` проверяет инструменты и сравнивает инвентарь с SHA базовой ветки. `covered` — блок, привязанный к Chrome-тесту (включая его HTML); `project-check` — блок во временном проекте. Это **не** результаты исполнения.
-   `Examples runtime (chrome)` выполняет оба вида проверок. Успех процесса без результата хотя бы одного ожидаемого теста не считается успехом. В Job Summary указаны отдельные числа для Chrome и для проверок проектов.
-   Старый неизменённый блок без проверки имеет статус `legacy`. Новый, изменённый или утративший покрытие блок приводит к ошибке. Подробный инвентарь со строками находится в артефакте `doc-examples-coverage`; результаты запусков и сгенерированные файлы — в `doc-examples-chrome`. Локальные пути: `tmp/doc-examples/` и `test/doc-examples/artifacts/`.
-   Для действительной сигнатуры, вывода или иного неисполняемого фрагмента укажите в `non-executable.json` страницу, язык, индекс блока (с нуля среди блоков того же языка), SHA-256 из отчёта и причину. Изменение кода потребует нового ревью. Для нативного Android-блока внутри настольной страницы укажите также `requires: "mobile"`.
-   Уже документированную возможность Grid, недоступную в локальном Chrome (например, управляемую загрузку файла), можно пометить `suite=selenium` только вместе с согласованным исключением по `exampleId`, хешу и причине. Такие блоки показаны как `requires-grid` и не исполняются. Не используйте исключения вместо теста для работающего примера.
