## Введение

Testplane запускает тесты в реальных браузерах и не привязан к конкретным версиям или одному источнику браузеров.

Вы описываете нужные браузеры в секции [`browsers`](../reference/config/browsers.mdx), а параметр [`gridUrl`](../reference/config/browsers.mdx#grid_url) определяет, откуда их брать: локально, из Docker-грида (например, Selenoid) или из удаленного облака (BrowserStack, Sauce Labs).

**Общая схема работы**

1. Testplane читает секцию `browsers`
2. Для каждого браузера берет `gridUrl` (общий или переопределенный на уровне браузера)
3. Обращается к гриду и запускает браузер с указанными `desiredCapabilities`

Обычно для всех браузеров используют один источник (один `gridUrl`), но при необходимости его можно задать отдельно для каждого браузера.

## Конфигурация браузеров

Секция [`browsers`](../reference/config/browsers.mdx) описывает, в каких браузерах запускаются тесты.

```ts title="testplane.config.ts"
import type { ConfigInput } from "testplane";

export default {
    browsers: {
        chrome: {
            gridUrl: "local",
            desiredCapabilities: {
                browserName: "chrome",
                browserVersion: "125.0",
            },
            windowSize: "1920x1080",
            headless: true,
        },

        "chrome-mobile": {
            gridUrl: "local",
            desiredCapabilities: {
                browserName: "chrome",
                browserVersion: "125.0",
                "goog:chromeOptions": {
                    mobileEmulation: {
                        deviceName: "iPhone 12 Pro",
                    },
                },
            },
            headless: true,
        },
    },
} satisfies ConfigInput;
```

Ключ в `browsers` (`chrome`, `chrome-mobile`) — логическое имя браузера. Оно используется в CLI и в отчетах. Имя не ограничивает реальные настройки: в `desiredCapabilities` можно указать любой `browserName` и `browserVersion`.

Версия браузера задается в `desiredCapabilities.browserVersion`. Для локальных браузеров Testplane скачает нужную версию, если она поддерживается.

`windowSize: "1920x1080"` задает размер окна, что важно для скриншотных тестов.

### Headless-режим

Параметр [`headless: true`](../reference/config/browsers.mdx#headless) включает запуск браузера без графического интерфейса.

**Важные моменты**

-   Поведение тестов идентично: с точки зрения тестов браузер с `headless: true` и `headless: false` работает полностью одинаково. Например, при запуске с `headless: true` все еще можно делать скриншоты, работать с DOM, выполнять любые команды.

-   Параметр обязателен в окружениях без UI: в окружениях, где нет графического интерфейса (например, в CI-джобах), необходимо использовать `headless: true`, иначе будут ошибки вида `cannot open display` и подобные.

### Мобильная эмуляция

Для Chrome используйте `goog:chromeOptions.mobileEmulation`:

```ts
const desiredCapabilities = {
    "goog:chromeOptions": {
        mobileEmulation: {
            deviceName: "iPhone 12 Pro",
        },
    },
};
```

Остальные поддерживаемые настройки смотрите в [официальной документации](https://developer.chrome.com/docs/chromedriver/mobile-emulation).

Для Firefox можно эмулировать мобильный user-agent через `moz:firefoxOptions`:

```ts
const desiredCapabilities = {
    "moz:firefoxOptions": {
        prefs: {
            "general.useragent.override":
                "Mozilla/5.0 (iPhone; CPU iPhone OS 14_0 like Mac OS X) AppleWebKit/605.1.15",
            "layout.css.devPixelsPerPx": "3.0",
        },
        args: ["--width=390", "--height=844"],
    },
};
```

## Локальные браузеры {/* #local-browsers */}

Самый простой способ начать работу с Testplane. Тесты запускаются на браузерах и драйверах, установленных на вашей машине.

### Установка зависимостей

Скачать все браузеры и драйверы, указанные в конфиге и поддерживающие автоматическую установку:

```bash
npx testplane install-deps
```

Загрузить только выбранные браузеры (по логическому имени из конфига):

```bash
npx testplane install-deps chrome-dark
```

Указать конкретные версии:

```bash
npx testplane install-deps chrome@130 firefox@104
```

По умолчанию браузеры и драйверы скачиваются в директорию `.testplane` в домашней папке пользователя. Путь можно изменить через переменную окружения `TESTPLANE_BROWSERS_PATH`:

```bash
TESTPLANE_BROWSERS_PATH=./node_modules/.testplane npx testplane install-deps
```

#### Удаление браузеров

Удалите директорию .testplane в домашней папке или каталог, указанный в `TESTPLANE_BROWSERS_PATH`.

### Поддержка браузеров {/* #browser-support */}

Ниже представлена таблица поддерживаемых браузеров:

| Браузер | Автозагрузка | Автозагрузка драйвера | Запуск webdriver |
| ------- | ------------ | --------------------- | ---------------- |
| Chrome  | +            | +                     | +                |
| Firefox | +            | +                     | +                |
| Edge    | −            | +                     | +                |
| Safari  | −            | +                     | +                |

Поддерживаемые версии браузеров в зависимости от ОС:

|   ОС    | Windows | MacOs | Ubuntu 20 | Ubuntu 22 | Ubuntu 24 |
| :-----: | ------- | ----- | --------- | --------- | --------- |
| Chrome  | 73+     | 73+   | 73+       | 73+       | 73+       |
| Firefox | 60+     | 60+   | 60+       | 91+       | 126+      |
|  Edge   | \*      | \*    | \*        | \*        | \*        |
| Safari  | −       | \*    | −         | −         | −         |

> `*` — автозагрузка браузера не поддерживается, но если браузер установлен пользователем, Testplane будет использовать установленную версию.

### Запуск тестов

Есть два варианта:

-   Через CLI-опцию `--local`:

```bash
npx testplane --local
```

-   Через `gridUrl: "local"` в конфигурации:

```ts title="testplane.config.ts" testplane-project=config
import type { ConfigInput } from "testplane";

export default {
    browsers: {
        chrome: {
            gridUrl: "local",
            desiredCapabilities: {
                browserName: "chrome",
                browserVersion: "125.0",
            },
            windowSize: "1920x1080",
            headless: true,
        },
    },
} satisfies ConfigInput;
```

### Плюсы и минусы

#### Преимущества

-   Высокая скорость запуска тестов
-   Нет затрат на облачные сервисы
-   Простая настройка и легкая отладка

#### Ограничения

-   Ограниченный набор версий браузеров
-   Зависимость от операционной системы: скриншоты могут различаться

Локальные браузеры подходят для разработки, быстрого прогона и отладки, но не идеальны для скриншотного тестирования между разными ОС.

## Браузеры в Docker-контейнерах

Docker-контейнеры дают изолированное и воспроизводимое окружение для локальной разработки и CI/CD. При `gridUrl: "docker"` Testplane скачивает образы, управляет Selenoid и контейнерами браузеров, а после прогона удаляет контейнеры и сеть. Образы сохраняются локально для следующих запусков.

### Установка Docker

<Tabs groupId="docker-os">
<TabItem value="linux" label="Linux" default>

1. Установите Docker Engine по [инструкции для вашего дистрибутива](https://docs.docker.com/engine/install/). Для Ubuntu используйте [инструкцию по установке на Ubuntu](https://docs.docker.com/engine/install/ubuntu/).
2. Выполните [шаги после установки](https://docs.docker.com/engine/install/linux-postinstall/), чтобы Docker работал без `sudo`. При стандартной установке добавьте своего пользователя в группу `docker`:

    ```bash
    sudo usermod -aG docker "$USER"
    ```

    Выйдите из пользовательской сессии и войдите снова, чтобы применилось изменение группы.

3. Проверьте доступ из терминала, в котором будете запускать Testplane:

    ```bash
    docker run hello-world
    ```

</TabItem>
<TabItem value="macos" label="macOS">

Рекомендуем [Colima](https://github.com/abiosoft/colima): она запускает Docker в Linux VM. Установите Colima и Docker CLI через [Homebrew](https://brew.sh/):

```bash
brew install colima docker
```

На Apple Silicon с macOS 13 и новее используйте нативную VM `aarch64` с `vmType: vz` и `rosetta: true`. Благодаря Rosetta образы браузеров `amd64` тоже работают с хорошей производительностью, если ARM-образ недоступен.

Создайте отдельный профиль Colima для тестов и откройте его конфигурацию:

```bash
colima start testplane --edit
```

Примените настройки ниже, сохраните файл и закройте редактор, чтобы запустить VM. На Intel Mac укажите `arch: x86_64` и `rosetta: false`.

<details>
<summary>Рекомендуемая конфигурация Colima для Apple Silicon</summary>

```yaml
cpu: 4
memory: 8
disk: 60
arch: aarch64
runtime: docker
vmType: vz
rosetta: true
mountType: virtiofs
autoActivate: true
network:
    address: true
    dns: []
docker:
    ipv6: true
    fixed-cidr-v6: fd7b:91d5:4c2a::/64
    ip6tables: true
    default-address-pools:
        - base: 172.30.0.0/16
          size: 24
        - base: fd7b:91d5:4c2a:100::/56
          size: 64
    dns:
        - 192.168.64.1
```

</details>

Настройки Docker включают IPv6 для стандартного моста и задают пулы IPv4/IPv6-адресов для сетей, которые создает Testplane. `docker.dns` задает DNS-сервер, доступный из контейнеров; `192.168.64.1` — пример для сети VZ. Проверьте DNS в своей VM командой `colima ssh testplane -- cat /etc/resolv.conf` и при необходимости замените адрес с учетом вашей сети или VPN. Оставьте `network.dns: []`, чтобы Colima использовала свой DNS-резолвер.

Если вы изменили конфигурацию работающего профиля, перезапустите его командами `colima stop testplane` и `colima start testplane`. Выберите его Docker-контекст и проверьте доступ:

```bash
docker context use colima-testplane
docker run hello-world
```

### Выбор образов браузеров

Используйте образы, собранные для Selenoid: при запуске контейнера они поднимают WebDriver-сервер браузера. Обычного Linux-образа или образа только с бинарным файлом браузера недостаточно. Порт и путь WebDriver должны соответствовать образу; значения по умолчанию — `4444` и `/`.

Готовые образы доступны в следующих источниках:

-   [Пакеты Gemini Testing](https://github.com/orgs/gemini-testing/packages), в том числе [`browsers/chromium`](https://github.com/gemini-testing/images/pkgs/container/browsers%2Fchromium).
-   Образы Aerokube на Docker Hub: [`selenoid/chrome`](https://hub.docker.com/r/selenoid/chrome/tags) и [`selenoid/firefox`](https://hub.docker.com/r/selenoid/firefox/tags). Их настройки описаны в [документации образов](https://aerokube.com/images/latest/).

Выберите тег версии на странице пакета. Для самостоятельной сборки используйте [`gemini-testing/images`](https://github.com/gemini-testing/images/). Для приватного реестра предварительно выполните `docker login`. Образ контроллера Selenoid уже задан в Testplane по умолчанию: выбрать нужно только образы браузеров.

### Запуск браузеров в локальном Docker {/* #local-docker */}

Укажите `gridUrl: "docker"` и образ для каждого браузера:

```ts title="testplane.config.ts" testplane-project=config
import type { ConfigInput } from "testplane";

export default {
    gridUrl: "docker",
    sessionsPerBrowser: 1,
    browsers: {
        chrome: {
            desiredCapabilities: { browserName: "chrome" },
            docker: { image: "ghcr.io/gemini-testing/browsers/chromium:126.0" },
        },
        firefox: {
            desiredCapabilities: { browserName: "firefox" },
            docker: { image: "selenoid/firefox:125.0" },
        },
    },
} satisfies ConfigInput;
```

Тег образа определяет версию браузера. `desiredCapabilities.browserVersion` не выбирает и не скачивает другой образ. Дополнительные настройки описаны в [справочнике `docker`](../reference/config/browsers.mdx#docker).

Запустите тесты:

```bash testplane-project=cli
npx testplane --browser chrome
```

Testplane автоматически подготовит образы и запустит нужные контейнеры. Самостоятельно запускать Selenoid или создавать `browsers.json` не нужно.

#### Доступ к приложению на хосте

Если приложение работает на хосте, запустите его, например на порту 3000, и задайте соответствующий `baseUrl`:

```ts testplane-project=config
export default {
    baseUrl: "http://host.docker.internal:3000",
    // ... остальные настройки
};
```

Внутри контейнера браузера `localhost` указывает на сам контейнер. Для доступа к хосту используется `host.docker.internal`. Приложение должно слушать интерфейс, доступный из контейнеров, например `0.0.0.0`. Абсолютные URL и редиректы тоже должны быть доступны из контейнера.

Testplane по умолчанию добавляет `host.docker.internal:host-gateway` для Docker. Если вы задаете `docker.hosts` и вам нужен доступ к хосту, включите эту запись в массив: он заменяет значение по умолчанию.

#### Подготовка образов для CI

Чтобы скачать и подготовить образы до этапа запуска тестов, выполните:

```bash
npx testplane prepare-docker
```

Эта [команда](../reference/cli.mdx#prepare-docker) подготавливает образы без запуска Selenoid и браузерных сессий. На Apple Silicon она также может собрать кешируемый образ с совместимым CDP-адаптером для `amd64`-образа Chrome или Яндекс Браузера. Выполняйте подготовку и тесты на одном Docker-демоне, чтобы использовать эти образы повторно. При обычном запуске такая же подготовка выполняется автоматически, поэтому отдельный шаг необязателен.

#### Платформы и параллелизм

При скачивании образа Testplane предпочитает нативную платформу Docker-демона. Если образ ее не поддерживает, Testplane использует `linux/amd64`, когда такая платформа доступна. На ARM-машинах для запуска такого образа нужна эмуляция, например Rosetta в Colima. Уже сохраненные локально образы для нативной платформы или `linux/amd64` используются повторно.

Чтобы зафиксировать платформу, задайте `docker.platform` для браузера и при необходимости `docker.selenoidPlatform` для Selenoid. При явно заданной платформе Testplane не переключается на другую архитектуру. Если локальный образ не соответствует настройке, скачайте или соберите его для нужной платформы.

Если все браузеры в конфиге используют Docker и `system.parallelLimit` не задан, Testplane автоматически ограничивает параллелизм значением `max(1, floor(CPUs × 5 / 4))`. Используется меньшее из чисел CPU, доступных Testplane и Docker-демону; если число CPU демона получить не удалось, используется локальное. Задайте [`system.parallelLimit`](../reference/config/system.mdx#parallel_limit), чтобы переопределить лимит, и `sessionsPerBrowser`, чтобы ограничить отдельные браузеры.

Можно задать `gridUrl: "docker"` отдельным браузерам, а для остальных использовать локальный запуск или удаленный грид. Флаг `--local` переключает прогон на локальные браузеры, даже если в конфиге задан Docker.

Если вам нужно управлять образами и контейнерами самостоятельно, перейдите к [ручной настройке Docker-грида](../guides/docker-grid.mdx).

### Плюсы и минусы

#### Преимущества

-   Единое окружение браузера для локального запуска и CI
-   Testplane управляет жизненным циклом контейнеров
-   Версии браузеров зафиксированы тегами образов

#### Ограничения

-   Нужны Docker и место на диске для образов
-   Потребляет больше ресурсов, чем локальные браузеры
-   Архитектура CPU может влиять на рендеринг: для сравнения скриншотов используйте одинаковые образ и платформу

## Удаленные гриды

Облачные сервисы (такие как BrowserStack и Sauce Labs) дают широкий набор браузеров, ОС и реальных устройств для кросс-браузерного тестирования.

### Подключение и аутентификация

Для подключения нужно указать `gridUrl` сервиса и передать учетные данные через `user` и `key`. Рекомендуется хранить их в переменных окружения.

Базовая конфигурация браузеров остается той же, меняется только `gridUrl`, и добавляются специфичные опции облачного провайдера:

```ts title="testplane.config.ts"
export default {
    browsers: {
        chrome: {
            gridUrl: "https://hub.browserstack.com/wd/hub",
            user: process.env.BROWSERSTACK_USERNAME,
            key: process.env.BROWSERSTACK_ACCESS_KEY,
            desiredCapabilities: {
                browserName: "chrome",
                browserVersion: "125.0",
                "bstack:options": {
                    os: "Windows",
                    osVersion: "11",
                    projectName: "My Test Project",
                    buildName: "Build 1.0",
                },
            },
            windowSize: "1920x1080",
            headless: true,
        },

        "chrome-mobile": {
            gridUrl: "https://hub.browserstack.com/wd/hub",
            user: process.env.BROWSERSTACK_USERNAME,
            key: process.env.BROWSERSTACK_ACCESS_KEY,
            desiredCapabilities: {
                browserName: "chrome",
                browserVersion: "125.0",
                "goog:chromeOptions": {
                    mobileEmulation: {
                        deviceName: "iPhone 12 Pro",
                    },
                },
                "bstack:options": {
                    os: "Windows",
                    osVersion: "11",
                    projectName: "My Test Project",
                    buildName: "Build 1.0",
                },
            },
            headless: true,
        },
    },
};
```

### Кастомизация сессий

У разных сервисов свои опции:

**BrowserStack** (`bstack:options`)

-   ОС и ее версия (`os`, `osVersion`)
-   Разрешение экрана (`resolution`)
-   Локальное тестирование (`local`)
-   Включение логов и отладки (`debug`, `networkLogs`, `consoleLogs`)

**Sauce Labs** (`sauce:options`)

-   Имя и билд (`name`, `build`)
-   Теги (`tags`)
-   Ограничения по времени (`commandTimeout`, `idleTimeout`, `maxDuration`)
-   Видео и логи (`recordVideo`, `recordLogs`)

### Таймауты и отладка

Облачные сервисы жестко ограничивают время выполнения одной команды, время простоя сессии и максимальную длительность сессии.

Для отладки доступны:

-   Логи сессий
-   Видео каждого прогона
-   VNC или аналог для просмотра браузера
-   Сетевые логи

### Плюсы и минусы

#### Преимущества

-   Широкий выбор браузеров, версий и операционных систем
-   Не требуется поддержка собственной инфраструктуры
-   Встроенные инструменты отладки: логи, видео, сетевые трассировки

#### Ограничения

-   Стоимость использования при большом количестве запусков
-   Зависимость от качества сети и возможные задержки
-   Жесткие ограничения по времени выполнения сессий

Облачные гриды подходят для кросс-браузерного и мобильного тестирования, когда нужен широкий охват платформ без затрат на собственную инфраструктуру.

## Как выбрать источник браузеров

Рекомендуется выбрать один источник браузеров для всего проекта (или для каждого пака тестов, если вы разбиваете их на группы). Выбирайте подход, который закрывает ваши основные потребности:

### Локальные браузеры для большинства проектов

Если вы не используете скриншотные тесты и вам важна скорость запуска (например, для разработки и отладки), локальные браузеры — самый простой и быстрый вариант. Они не требуют дополнительной инфраструктуры и работают прямо на вашей машине.

### Docker для стабильных скриншотов

Когда важна стабильность скриншотов между разными машинами и операционными системами, а вы готовы работать с Docker-образами, используйте Docker. Используйте одинаковые образ браузера и платформу локально и в CI, чтобы свести различия рендеринга к минимуму.

### Облачные гриды для масштабирования

Если вам нужна стабильность скриншотов, высокая параллельность на тысячах тестов или тестирование на множестве комбинаций браузеров и ОС, подойдут облачные гриды. Вам не придется поддерживать свою инфраструктуру, также будет доступен широкий набор браузеров и устройств. Недостатком будет стоимость при большом количестве запусков.

<Admonition type="tip">
    Для разработки и отладки можно использовать локальные браузеры (запуск с `--local`), даже если в
    CI используется Docker или облако. Это ускорит итерации при написании тестов.
</Admonition>

## Отладка

Есть два способа включить подробные логи.

1. Через конфигурацию:

    ```ts title="testplane.config.ts"
    export default {
        browsers: {
            // ... ваши браузеры
        },
        system: {
            debug: true,
        },
    };
    ```

2. Через переменные окружения (с ограничением уровня логирования `webdriverio`):

    ```bash
    testplane_system_debug=true WDIO_LOG_LEVEL=error npx testplane --local -b chrome
    ```
